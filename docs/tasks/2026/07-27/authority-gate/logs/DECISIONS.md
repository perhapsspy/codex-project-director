# 결정 기록

**2026-07-27**

- **배경:** 디렉터가 승인된 Goal 수행 중 발견한 의존성을 “완료에 필요하다”는 이유로 새 구현 작업 흐름으로 승격할 수 있었다.
- **결정:** Authority Gate를 Goal·실행 유지·복구보다 먼저 적용하고, 변경 작업에는 사용자 승인 대상·영역·허용 효과·담당자 네 필드를 모두 요구한다.
- **이유:** 계획 포함, 조사 승인, 작업자 제안과 완료 필요성은 범위 판단의 증거일 수 있지만 mutation 권한의 출처는 아니다.
- **영향:** 발견과 승인 범위 내 복구는 현재 담당자에게 남긴다. 기존 레코드 밖의 변경 제안만 `NEEDS_DECISION`으로 보고하며 liveness와 복구는 승인된 작업 안에서 계속 작동한다.

**2026-07-27**

- **배경:** 기존 스킬은 모든 활성 디렉터 세션에 Charter·State 파일을 만들도록 해 감독 지정만으로 프로젝트 파일 변경 권한이 생기는 우회로가 있었다.
- **결정:** 조정 영역의 쓰기도 사용자 승인이 있을 때만 수행하고, director가 작성한 charter·plan은 명시적 사용자 승인을 기록할 뿐 스스로 권한을 부여하지 못하게 한다.
- **이유:** 상태 보존 필요성 역시 mutation 필요성일 뿐 권한 출처가 아니며, Authority Gate의 기본값과 일치해야 한다.
- **영향:** 쓰기 권한이 없으면 조정 상태는 읽기 전용·세션 내부로 유지하고, 필요한 경우 지속성 한계만 보고한다.

**2026-07-27**

- **배경:** 사용자가 의존 작업을 독립 세션으로 분리한 뒤에도 기존 디렉터가 Goal이나 완료 조건에 남겨 감독을 이어갈 수 있었다.
- **결정:** 사용자 분리 시 한 번의 사실 인계 뒤 해당 작업을 Charter·State·Goal·완료 주장·감독에서 제거하고 다시 확인·통합·회수하지 않는다.
- **이유:** 독립 분리는 실행 담당자만 바꾸는 것이 아니라 이 디렉터의 권한과 상태 소유권을 끝내는 사용자 지시다.
- **영향:** 남은 목표에 미치는 영향은 보고할 수 있지만, 그것을 이유로 분리된 작업의 소유권을 되찾을 수 없다.

**2026-07-27**

- **배경:** 초기 Authority Gate 후보가 같은 금지를 Goal·복구·상태 절에 반복하고, 최신 사용자 발화와 기존 권한의 관계 및 분리된 작업이 남은 완료 기준에 미치는 영향을 모호하게 만들었다.
- **결정:** 현재 유효한 권한을 `Outcome·Surface·Effect·Owner` 레코드로 표현하고, 일치하는 행동의 실행을 정상 경로로 둔다. 분리 시 레코드와 감독을 종료하되 남은 Goal의 완료 영향은 별도 `NEEDS_DECISION`으로 판단한다.
- **이유:** 권한 계약의 정본을 한곳에 두면 liveness·복구가 같은 경계를 참조하면서도 금지문 반복 없이 적극적으로 작동한다.
- **영향:** “계속해”는 기존 레코드를 유지하고, director는 승인된 결과·영역·효과 안에서 명시적 담당자를 교체할 수 있다. 새 사용자 가시 작업자 생성과 고위험 효과는 계속 별도 사용자 권한을 요구한다.

**2026-07-27**

- **배경:** `Outcome·Surface·Effect` 일치 판정이 정의되지 않으면 같은 저장소, 구조적 의존성이나 완료 필요성을 기존 권한의 해석으로 포장할 수 있었다.
- **결정:** 세 필드를 각 사용자 권한 근거와 독립적으로 대조하고, 영역·효과의 적용이 모호하면 `NEEDS_DECISION`으로 판정한다. 담당 이전은 같은 레코드의 기존 작업자에게만 허용하며 새 작업자는 명시적인 사용자 요청을 요구한다.
- **이유:** 권한 확대를 “기존 범위 해석”으로 우회하는 경로를 닫으면서 승인된 경계 안의 일반 구현 판단과 복구는 유지한다.
- **영향:** 같은 저장소의 새 의존성도 자동 포함되지 않는다. 레코드가 없는 발견 사항을 독립 분리할 때도 존재하는 레코드만 종료하고 디렉터 상태에서 완전히 제거한다.

**2026-07-27**

- **배경:** `RUNNING`이 상태 이름만으로 유지되고 다음 사건이나 점검 시점이 빠지면 디렉터와 작업자가 함께 유휴 상태에 머물 수 있었다. 반대로 고정 주기 확인은 정상 작업을 방해하고 토큰을 소비한다.
- **결정:** 각 `RUNNING`에 다음 사건과 판단 기반 점검 시점을 두고, 유효한 작업을 묶어 사건 기반으로 기다린다. 점검 시점에는 영향 작업만 한 번 확인하고 같은 범위의 재개·막힘 보고 지시도 한 번만 보낸다.
- **이유:** 판단을 바꾸는 증거 부재를 개입 신호로 삼으면 정상 장기 작업의 자율성과 감독의 실행 책임을 함께 유지할 수 있다.
- **영향:** 새 실행 증거나 실질적 진전이 실행 유지 근거다. 이어지는 침묵이나 상태 보고는 `BLOCKED`, 사용자 선택이나 권한이 필요한 복구는 `NEEDS_DECISION`이며, `RUNNING`이 남은 동안 디렉터는 사건 기반 감독을 유지한다. 완료 사건은 해당 작업을 한 번 읽어 결과와 증거를 회수한다.
